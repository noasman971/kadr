# 0010. The MCP server is built on `rmcp`, with tools defined in `kadr-tools`

- Status: Accepted
- Date: 2026-11-26

## Context

Phase 5 exposes Kadr's editing tools to Claude Desktop and Claude Code through
the Model Context Protocol, over stdio (decision 0004). The specification names
`rmcp`, the official Rust SDK, and asks to check it first. The tools must also be
reusable without MCP: phase 7 lets the desktop app run the same tools, and the
spec wants each tool defined once (name, description for a language model, JSON
schema, execution).

## Options considered

1. **`rmcp` with its `#[tool]` macros**: each tool is a method of the server,
   parameters derive `JsonSchema`. Little code, but the tool definitions then live
   in the MCP crate and depend on `rmcp`'s types and macros: the desktop app could
   not reuse them without MCP.
2. **`rmcp` with a hand-written `ServerHandler`** over a transport-free tool
   catalogue in `kadr-tools`: `kadr-tools` declares each tool (parameters as a Rust
   struct deriving `Deserialize` + `schemars::JsonSchema`, description, code);
   `kadr-mcp` only lists them and turns their answers into MCP content.
3. **Our own JSON-RPC over stdio**: no dependency, but we would re-implement
   initialisation, version negotiation, cancellation and the evolving MCP schema,
   which the official SDK already tracks (3.11 supports every protocol version up
   to 2026-07-28).

## Decision

Option 2, with `rmcp` 3.11.0 (Apache-2.0), features `server` and `transport-io`
only (no HTTP, no authentication).

- `kadr-tools` has no MCP dependency. `KadrToolbox::tool_definitions()` gives each
  tool's name, title, description and JSON schema; `KadrToolbox::call_tool(name,
  arguments)` runs it and returns text and pictures (`ToolOutput`).
- Schemas are generated by `schemars` 1.2 from the parameter structs, with
  sub-schemas inlined (no `$ref`) and field documentation as descriptions, so the
  schema Claude reads cannot drift from the code reading the arguments. Unknown
  fields are refused (`deny_unknown_fields`), so a typo is reported, not ignored.
- `kadr-mcp` implements `ServerHandler::list_tools` and `call_tool`. A call runs
  on a blocking thread (`spawn_blocking`) behind a mutex: tools decode video and
  render, and one project has one undo history, so calls are made one at a time.
  Long exports run on their own threads (task ids), so the mutex is never held
  for long.
- Tool failures are returned as tool results with `isError: true` and a message
  in plain words, never as protocol errors, which clients hide from the model.
- Pictures are JPEG, base64 in MCP image content.

## Consequences

- The desktop app (phase 7) can run the same tools by calling `KadrToolbox`.
- Adding a tool = one parameter struct, one description, one function, one line
  in the catalogue. The integration tests check every tool has a schema, a
  description and described parameters.
- `rmcp` moves fast (major versions follow the MCP specification): upgrades may
  need small changes in `kadr-mcp` only.
